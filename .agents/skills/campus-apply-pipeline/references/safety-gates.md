# 授权、资格与结果边界

## 授权范围

用户意图决定筛选、准备或投递范围。已授权任务可跨轮次继续；「继续」「已登录」可以续接该任务，但不能扩展到其他公司或额外批量申请。仅检查/优化 skill 不授权实际投递、上传或看板写入。

## 工作区与多用户严格隔离边界

- **唯一数据根路径**：本机可能存在其他用户的自动化投递环境或系统级全局目录。**本任务涉及的所有候选人事实、简历文件（PDF/DOCX）、配置文件（config.json）、私有档案（work/application_profile.json）、执行断点、证据截图与输出，必须 100% 局限并解析自当前工作区根目录（`D:\auto-delivery\`）！**
- **严禁跨目录逃逸**：绝对禁止读取或写入主机 `C:\Users\...` 及任何非本工作区的外部目录文件，杜绝多用户间简历附件、身份事实、凭据与投递历史的串扰。
- **简历文件本地化**：简历附件统一存放并引用自 `<工作区根>/data/resume/`，配置与档案只以当前目录相对路径解析。

上传与填写会向招聘方提供个人资料。确认实际公司/岗位、文件、站点及已有授权；按用户明确授权的文件和用途范围复用许可，包括固定简历在今后已授权求职任务中的跨公司上传授权；有此持续授权时，不因招聘方变化再次询问。此授权不扩大投递数量、邮箱发送或其他任务范围。同一载荷和目的地在原范围内已获授权时不重复询问。若自动审批明确拒绝动作，停止该动作，不换工具或改成间接执行；说明具体动作及拒绝原因，补齐所需授权后再继续。用户换岗、撤回授权或修改红线时先更新目标和断点。

需要用户接管登录、验证或缺失信息时，说明真实网站/工具原因；遵守当前使用工具的确认与接管要求。技能本身不授予绕过验证码、访问控制或额外通信的权限。

## 岗位资格与偏好

- 仅校招范围；目标届别以用户资料为准。标题含校招/秋招/实习只能发现线索，还要核实适用毕业时间、学历及批次。
- 官网明确社招、学历硬性不符、错届、下线或截止则跳过。未知资格保留待核实，不能当 PASS。
- 用户的岗位排除词同时检查标题与职类；JD 中「数据结构与算法基础」不单独等于算法岗位。
- 语言、城市、Java 主栈等按已确认偏好和岗位主体要求判断，不因技能清单出现一个词就扩张红线。
- 城市优先级及志愿排序读取已确认资料，结合实际 JD 和工作地排序；优先级本身不是异地排除或调剂授权。
- 采集日期不是截止时间；未公开截止时间不得编造。

## 公司级去重与多岗位配额策略

默认公司级去重，延续用户已有去重政策。投前查询本地断点、看板和官网记录，考虑公司简称/全称；不能只按完全相同的字符串比对。公司相似但身份不明时先核实，不把短字串包含当作确定身份。

- 有已投记录：按公司级政策跳过；要改资料走原申请编辑入口。
- 用户明确授权同公司多岗位时，在本次请求的公司、岗位和数量范围内，按其已确认的多岗位策略选择合适岗位；网站还有配额不自动扩大本次授权。同岗位依然不重复提交。
- 用户已授权跨公司并行时，可在本次范围内分标签推进；每个任务独占对应标签和断点，遵守浏览器服务的任务锁。同一公司配额及看板回写须协调串行，避免冲突。
- 解析后逐项核对教育、实习、项目、奖项等记录的身份、时间与描述；网站支持独立条目时按真实来源数量分别保留，不能合并、串段或虚增。无法保存正确事实时停止提交并说明。
- 查询失败、响应缺失或异常：状态未知，不当作未投递。
- 提示近期已投/无法内推：先查既有申请；不能直接切直投再次提交。仅在证实没有申请、确为渠道不可用且原授权涵盖替代渠道时换入口。
- 最早可能提交的动作前保存 `awaiting_verification` 断点并只读核验（含「预览并提交」、验证码后自动提交），流程与证据强度见 [application-playbook.md](application-playbook.md) §5。

单轮数量上限是限制，不是批量投递授权。

## 真实资料

缺失必填集中询问；可选项可留空。不编造国籍、学位、排名、亲属任职、政治面貌、日期或技能水平。排名档位只能选择真实名次确实落入的范围，不能抬高。

最新确认覆盖旧简历与解析值，并保留来源和范围；不把某公司答案变成全局偏好（可入全局档案的只有与投递对象无关的客观事实，判定见 `D:\auto-delivery\resume-autofill\SELF_LEARNING_LOOP.md` §4 三级晋升）。证件号码没有既有授权事实时交用户当次填写，不存入通用档案。

## 浏览器与凭据

复用用户已授权的浏览器/已登录会话；不同浏览器、资料目录和企业门户之间不得假定共享登录。只记录网站、资料目录标识、检查时间和登录状态等必要元数据，不保存 cookie/token。不要自行复制 profile、导出认证 cookie、延长 cookie 有效期、改安全设置、关闭整批标签页或杀掉浏览器进程。站点会话失效时按网站正常流程重新登录或请用户接管；不保证不再出现验证。

短信同步服务须已获用户授权，且只读取这次登录相关的新消息：发送前记录基线，校验发送方/服务、接收账号、请求后时间及消息新鲜度；基线 ID 增大本身不足以证明验证码归属。不把其他验证码或旧短信试进表单，不在日志输出完整收件内容。服务不可用时请用户提供或手动登录，不自动部署服务。

密码、一次性验证码及挑战答案不落盘。遵守浏览器/桌面工具的登录与验证码限制，不自挂验证实例、伪造/复用挑战 token 或绕过网站校验。

## 验证码边界（单一真源）

按**控件类型**一刀切，不按站点记忆、不看哪个 agent 上次怎么做的：

| 类型 | 谁做 | 判据 |
|---|---|---|
| 点选型（GeeTest 点选、图片九宫格） | agent 可做 | 先截整图定位目标格 → 逐格可信点击 → **再截一张核对选中态** → 确认；一格都不猜 |
| 滑块拼图 | 用户 | 拖拽轨迹即行为特征，agent 不代拖；保留标签页并写断点 |
| 短信 / 邮件验证码 | 用户 | 先确认真的发出（看倒计时/发送反馈），按正常入口提交 |
| 字符图形码 | 用户 | 不做 OCR 猜测 |

- 任一类**失败一次即停**，不在同一页面循环重试，不改写验证接口。
- 每次处理都落进断点：`needs_human=captcha_point|captcha_slider` + `reason` 写一句为什么停。
- 点选完成后仍按 [application-playbook.md](application-playbook.md) §5 存 `awaiting_verification` 断点，再提交。
- 样板：2026-10-31 泰康 GeeTest 点选 4 格喷泉，先截图核对选中态再确认 —— 属「agent 可做」。

## 成功与回写

成功必须属于本次目标及新申请：优先验证官网应聘记录中的公司、岗位 ID/名称、时间或唯一申请编号；成功页、截图和配额变化作为可用的交叉证据。旧成功页、上传成功、解析成功、点击返回值、通用自动化 `success=true` 均不能独立证明投递成功。

记录入口暂不可读时保留待核验；门户没有可用记录入口时，官方明确成功页须同时关联本次目标及本次新增申请的唯一标识，才可确认。证据不足保持未知，不能为了取证重投。

只有 `submitted` 才写已投递记录。`draft`、`needs_input`、`awaiting_verification`、`blocked`、`skipped` 只留本地和对话。回写超时先查询是否已登记；仅补记已有成功申请，不重新提交申请。未验证回写就说明待核实，不把它算作已同步。
