# 岗位发现、资格与筛选

先确认平台，再选择读取方法。以下 URL、选择器和布局是曾见过的形式，均须核验当前页面；不是跨门户保证。

## 通用流程

1. 复用现有搜索/评分工具与平台流程。公共页面可先 HTTP 读取；需要登录或动态渲染时复用已授权浏览器，不为抓列表另建无头 profile。
2. 搜索摘要或列表仅发现线索；入围后读实际详情，核对主体标题、公司、岗位 ID、职类、城市、学历与批次。推荐区同名岗位不算当前岗位证据。
3. 对照资料中的目标毕业届别/时间、岗位红线与公司级去重政策。资格不明先待核实；明确不符/下线/截止则排除。
4. 采用已有评分权重，记录真实优势、缺口与未知项；未填画像模板不得当作事实。
5. 输出岗位、城市、批次、职类、理由及来源链接。搜索/找岗模式停在清单；已有投递授权时可在原范围内继续。

只读取任务需要的页数。翻页记录页码和岗位 ID，检测重复页、禁用下一页或列表不变即停；不默认遍历几十页。404/403/空壳先核验官方替代入口；检索仍失败报不可读取，不能把未知说成已截止。

## 飞书招聘

- 常见路由：`/campus/position/list`、`/campus/position/{id}/detail`、`/campus/resume/{id}/apply`。
- 部分列表接受 `?keywords=`；`?page=`、`.atsx-pagination-next` 等须在当前页面实测，不能仅改 URL 后假定已经翻页。
- 实际详情或当前列表卡片中的职类很关键：标题写「开发工程师」仍可能归为算法；用户排除算法时一起核对。
- 配额及表单 schema 可能在初始渲染后才加载；等目标信息、当前额度和可用控件齐全，不用默认模板数值推断剩余额度。
- 下线提示优先于搜索引擎摘要。没有公开截止日期时写未公开，不从采集时间推算。

## 北森 zhiye / italent

- 不同门户可能是 `zpdetail/{id}`，也可能是 `/campus/detail?jobAdId=...`；SPA 需要渲染。
- 在实际目标卡片上展开后点击可见申请按钮，检查是否另开详情/表单标签；空弹层本身不能证明无法自动点击。
- 表单顶部职位和 URL 中岗位标识应一致，再处理简历。
- 各门户登录入口与登录状态可能不同；账号体系相似不证明跨公司已登录。按当前门户提供的扫码/短信方式操作。

## 应届生 / 51job xyz

- 岗位可能在 `campus.51job.com` 公司页、站点正常公开接口或页面资源中；读取当前公开请求约定，不使用文档缓存的密钥或签名常量，不绕过登录/访问控制。
- 常见申请路由为 `xyz.51job.com/external/apply.aspx?jobid=...&ctmid=...`，只在页面实际给出或验证一致后使用。
- 不同公司模板必填项不同；已有账号/简历可复用，高中等新增必填没有来源时集中询问。
- 末步可能有 iframe 附件上传器，必须核验服务器已接收附件，而非仅选中文件。

## 其他渠道

| 渠道 | 处理方式 |
|---|---|
| BOSS、国聘、前程无忧、猎聘等 | 保留现有登录、筛选及投递方式；按用户目标届别核实应届条件，不因本技能没有配方就改为人工或社招 |
| wondercv / 超级简历等第三方入口 | 先检查已确认渠道偏好；用户明确排除时不要登录或使用该渠道 |
| hotjob | 故障时查官方可用入口；更换子域后重新核验公司/岗位 ID，不把相似路径当同一申请 |
| 邮箱/公众号公告 | 提取岗位及联系方法；现有网申授权不自动扩展为发邮件，只有用户另有明确指令才发送 |

## 画像约束与志愿策略

- **Base 优先级排序铁律**：
  * **第一优先：江浙沪长三角（上海、杭州、南京、苏州、宁波等）**
  * **第二优先：深圳地区（大湾区核心）**
  * **第三优先：其他城市（如成都，作为就读地次选；长沙、北京等作为补充）**
  多志愿排序综合岗位 JD 契合度与 Base 优先级；有长三角或深圳岗位的企业，长三角/深圳岗位排第一志愿，不能因为就读在成都就把所有志愿都选成都。
- **多岗位配额穷尽原则**：对支持多岗位投递的企业（如北森 2~5 岗、电科网安 5 岗、泛联新安 2 岗、玖治 2 岗等），只要还有剩余配额且存在符合画像的研发岗，在单次任务中尽量把配额投满。
- **排除红线**：排除算法岗时查岗位标题与职类（如标题带算法或职类归为算法研究/训练主体），不因基础要求提及「数据结构与算法」误杀开发岗；Java 主栈岗位明确不投；社招/非当届错届岗位不投。
- **无匹配岗位的远端看板双向闭环机制**：
  经核实全站无匹配岗位（如全量算法红线、Java 主栈红线、纯销售/产品、或 Base 地严重不符）的公司，**通过直写 API 将状态更新为终止（`update_application(company, status="终止")`）或 `upsert_job`**，触发看板后端的封锁集机制（自动写入已结束招聘并移出岗位池），避免死循环重复推荐；具体原因如实向用户报告，不经对话接口（chat 端点已 410 废弃）。若用户后续明确指示恢复（如中通服设计院），则通过直写 API 撤销封锁并恢复岗位池。
